## 使用场景

当需要对已采集的 GitHub Trending 技术内容进行深度分析、总结和趋势发现时，使用此技能。适用于从 `knowledge/raw/` 读取原始采集数据后，执行逐条深度分析并生成结构化分析报告。

## 执行步骤

### 1. 读取采集文件

从 `knowledge/raw/` 目录读取最新采集文件（按文件名按日期排序，取最新文件）。例如 `knowledge/raw/github-trending-YYYY-MM-DD.json`。

解析为结构化条目数组，确保每条包含 `name`, `url`, `summary`, `stars`, `language`, `topics` 字段。

### 2. 逐条深度分析

对每条采集条目的开发，逐一执行深度分析，生成以下字段：

**要求：**
- 每条技术内容必须用 <= 50 字写总结（简洁扼要，中文）

- 提取 2-3 条技术亮点（必须引用**具体事实**：如使用了什么技术栈、架构设计独特之处、对比同类项目的突破点），如使用了什么最新框架、应用场景是什么（避免空泛评价如"有用"、"值得关注"，不使用明显的形容词如"值得了解"）
- 根据以下评分标准给出 1-10 分综合评分，**必须附理由**（不能超过事实支撑，不能凭空推断融资、团队等信息（如无线索则留空字符串））
- 根据内容建议 3-8 个标签（优先使用赛道分类：`LLM`、`Agent`、`RAG`、`向量数据库`、`AI 框架`、`AI Infra`，补充细粒度技术标签如`PyTorch`、`Kubernetes`、`GPU`、`分布式` 等，**避免空泛标签如"新技术"、"有用"**）

### 3. 趋势发现

对全部条目进行整体分析，识别出：

- **共同主题**：多条项目同时关注的技术方向或趋势
- **新概念**：本周首次出现的技术概念或新兴赛道
- **赛道映射**：将每个项目映射到关注赛道（LLM、Agent、RAG/向量数据库、AI 框架、AI Infra）

## 评分标准

| 分数段 | 定位 | 说明 |
|--------|------|------|
| 9-10 | 改变格局 | 具有颠覆性创新，可能改变行业或技术生态 |
| 7-8 | 直接有帮助 | 采用了有效方法或技术，对从业者有直接参考价值 |
| 5-6 | 值得了解 | 有意义但影响力有限，值得关注但不必立即深入 |
| 1-4 | 可略过 | 价值有限，仅与极少数场景相关 |

**约束：15 个项目中，9-10 分的项目不得超过 2 个。**
**如超过，必须向下调整分数。**

### 4. 输出分析结果 JSON

将分析结果以 `JSON 数组` 形式输出到 stdout 中，每项追加原始条目的字段并新增分析字段：

```json
[
  {
    "name": "owner/repo",
    "url": "https://github.com/owner/repo",
    "summary": "中文摘要一句话",
    "stars": 12345,
    "language": "Python",
    "topics": ["AI", "Agent", "LLM"],
    "analysis": {
      "summary": "2-4 句中文深度摘要（<= 50 字）",
      "highlights": ["亮点 1 具体事实", "亮点 2 具体事实"],
      "score": 8,
      "score_reason": "理由：基于具体事实，如使用 XX 框架，解决 XX 问题",
      "track": "Agent"
    }
  }
]
```

**注意**：`analysis.summary` 字段**不得超过 50 个字符**（含标点）。如果超过，必须压缩精简。

**字段说明：**

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `analysis.summary` | string | 是 | 2-4 句中文深度摘要（**不超过 50 字**） |
| `analysis.highlights` | string[] | 是 | 技术架构亮点或创新点列表（每条**必须引用具体事实**） |
| `analysis.score` | decimal | 是 | 综合所有锁定范围外为 1-10 范围内） |
| `analysis.score_reason` | string | 是 | 评分理由：基于具体事实说明分数 |
| `analysis.track` | string | 是 | 赛道标记（LLM、Agent、RAG、向量数据库、AI 框架、AI Infra） |

## 质量自查清单

分析完成前，必须执行以下自检：

- [ ] **摘要字数**：每条 `analysis.summary` 字符数 <= 50 字（含标点）
- [ ] **评分一致性**：所有条目的 `analysis.score` 存在且值在 1-10 范围内
- [ ] **9-10 分约束**：9-10 分的项目不超过 2 个（核心约束）
- [ ] **信息完整**：每个有效条目的 `analysis.summary`、`analysis.highlights`、`analysis.score`、`analysis.score_reason`、`analysis.track` 均非空
- [ ] **事实核查**：分析和亮点必须基于实际抓取的内容（不涉及从输入内容中推断融资、团队、商业化等情况（如无线索则留空字符串））
- [ ] **语言规范**：`summary`、`analysis.summary` 均为中文，`highlights` 必须**引用具体事实**（不使用模糊形容词：如"值得了解"、"有潜力"。
- [ ] **标签规范**：避免空泛标签如"新技术"、"有用"等

## 注意事项

- **评分约束是硬性要求**：15 个项目中，9-10 分的不超过 2 个。如原始数据中有 3 个及以上符合"改变格局"标准，必须向下调整，留至多 2 个可以评为 9-10 分。
- `analysis.highlights` 必须引用**具体事实**（如"使用了 RAG 技术实现知识检索，支持多模型"），**不得**写成"技术先进"、"开发高效"等空泛评价。
- 对已知关注赛道（LLM 主流 AI 框架外（可选微调模型等方向）的项目，必须提供差异比较分析。
